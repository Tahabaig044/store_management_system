# Phase 0.1 — Database Entity Map

**Scope:** Pure evidence-based audit of `backend/prisma/schema.prisma` (1,929 lines, read in full) and the 11 migration folders under `backend/prisma/migrations/`. No code changes were made. No fields are invented — anything not explicitly present in the schema is marked "unclear" or "none". Deletion-behavior claims are taken directly from the `ON DELETE` clauses in the generated migration SQL (152 foreign keys inspected), not inferred from Prisma defaults.

**Entity count:** 63 `model` blocks in `schema.prisma` (documented below). A further 3 tables exist only in an unapplied, paused migration and are **not** counted among the 63 — see Cross-Cutting Finding D.

Tables are grouped by domain: Identity/Tenancy, Master Data, Commerce, Procurement, Inventory/Warehouse, Finance/Accounting, Clinical/Optical, Communication/AI, Other.

Legend for **Deletion Behavior**: "Cascade(tenant)" = row is deleted when its `Tenant` is deleted (all 63 tenant-scoped models except pure line-items have this). Behavior of *other* relations is stated per entity as SET NULL / RESTRICT / CASCADE as found in the actual migration SQL.

## Cross-Cutting Findings

### A. Duplicate/overlapping concepts — candidates for a future universal entity model

1. **Six parallel "document with line items" workflows.** `Sale`, `Purchase`, `PurchaseOrder`, `PurchaseRequest`, `OpticalOrder`, and `StockTransfer` each independently implement the same recurring shape: a header with `tenantId`, an optional `branchId`, a status enum, an `idempotencyKey`, actor fields, and a separate `*Item` child table with `productId`/`quantity`/pricing. Money-bearing ones (`Sale`, `Purchase`, `PurchaseOrder`) additionally repeat `subtotal`/`discount`/`tax`/`total`/`amountPaid` verbatim. This is the strongest concrete candidate for a single generic "Order/Document" header + line-item schema with a `type` discriminator when generalizing to a universal Business OS — today, adding a 7th document type means a 7th full table pair, not configuration.
2. **Refraction data duplicated three times with no shared type.** `Prescription`, `Examination`, and `ClinicalPrescription` each carry an identical od/os Sphere/Cylinder/Axis/Add + `pd` field set. This is deliberate (each has a distinct immutability/versioning role per the schema's comments), but there is no shared embeddable/value-object type — a refactor candidate, and in any case fully ophthalmic/industry-specific, with no generic-Business-OS equivalent.
3. **Two incompatible polymorphic-reference patterns coexist.** `Payment` links to its source via six separate nullable FK columns (one per possible target: sale/purchase/customer/supplier/expense/opticalOrder). `JournalEntry` and `AiForecast` instead use a `sourceType` (or `scope`) enum paired with a loosely-typed `sourceId`/`scopeId` string (not a real FK either). Both patterns have different tradeoffs (referential integrity vs. extensibility); a universal platform should pick one and standardize.
4. **Fixed enums hard-code vertical-specific values alongside generic ones.** `AutomationEvent` (7 of 18 values are optical/appointment-specific) and `TemplateType` (9 of 15 values are optical/appointment-specific) are the clearest structural evidence that the "Optical/Clinic" vertical is coupled directly into core Prisma enums rather than being configuration. Extending either to a new industry today requires a schema migration, not a data change — the single most concrete blocker to treating Optical/Clinic as a swappable "industry pack."
5. **Inconsistent actor/"who did this" referential integrity.** Roughly half of the `*ById` actor fields across the schema are real relations to `User` with an FK, an index, and a defined `onDelete` (e.g., `PurchaseRequest.requestedById/approvedById`, `Sale.cashierId`, `Purchase.createdById`, `JournalEntry.postedById`, `Message.triggeredByUserId`, `Notification.userId`, `AiConversation.userId`), while the other half are bare, unconstrained `String` columns with no FK at all: `PurchaseOrder.createdById`/`approvedById`, `GoodsReceipt.receivedById`, `StockTransfer.requestedById`/`approvedById`/`dispatchedById`/`receivedById`, `Appointment.createdById`, `Examination.createdById`, `ClinicalPrescription.createdById`, `AutomationRule.createdById`, `AiForecast.generatedById`, `AiInsight.acknowledgedById`/`dismissedById`, `AiUsageLog.userId`, `AiFeedback.messageId`. This is a data-integrity/auditability gap, not a tenant-isolation issue, but it means "who performed this action" cannot be reliably joined or protected from referencing a deleted/nonexistent user in roughly half the schema.

### B. Missing or inconsistent tenant/branch keys

- **No direct `tenantId` on 16 child tables — Critical-risk latent data-isolation pattern.** The following tables carry no `tenantId` column at all and are scoped *only* through their parent's foreign key: `SaleItem`, `PurchaseItem`, `PurchaseRequestItem`, `RFQItem`, `RFQSupplier`, `SupplierQuotationItem`, `PurchaseOrderItem`, `GoodsReceiptItem`, `StockTransferItem`, `WarehouseStock`, `JournalLine`, `Prescription`, `AiMessage`, `CustomerCommunicationPreference`, `CustomerPortalOtp`, and `UserBranchAccess`. This is a common and often-acceptable pattern for pure line-item children *provided every query path joins through the parent*. This audit is schema-only (query/application code was not reviewed here), so no breach is confirmed — but the schema itself provides **zero defense-in-depth** for these 16 tables: a future raw query, report, or new endpoint written directly against e.g. `warehouse_stocks` or `sale_items` without joining back to `warehouses`/`sales` for a tenant filter would have no schema-level guardrail against cross-tenant leakage. Flagged as **Critical-risk** given the project's explicit "every tenant-owned table carries tenantId" design principle (stated in the schema's own header comment), which these 16 tables do not follow.
- **`OpticalOrder` has no `branchId` at all**, unlike `Sale`, `Purchase`, `Expense`, `PurchaseRequest`, `PurchaseOrder`, `JournalEntry`, `Message`, `AiInsight`, `Appointment`, `Doctor`, and `Warehouse`, all of which received a nullable `branchId` (several explicitly backfilled in the Phase 4/6 migrations per in-schema comments). Optical job-orders therefore cannot be filtered or reported on by branch the way sales/purchases can — an inconsistency worth resolving.
- **`Payment` has no `branchId`** despite representing money movement for branch-scoped Sales/Purchases/Expenses. Branch-level cash reporting must join back through `sale`/`purchase`/`expense`, which is impossible for a bare customer/supplier-balance payment with none of those links set — a real multi-branch reporting gap.
- **`Branch.code` is not tenant-unique-constrained** (no `@@unique([tenantId, code])`) despite the schema comment describing it as a short code a tenant "picks its own convention" for — two branches under the same tenant could silently share a code.
- `StockTransfer` having no direct `branchId` is judged **not** a flaw: a transfer can legitimately span two different branches' warehouses, so a single branch key would be ill-defined there.

### C. Destructive migration check

All 11 migration folders (`20260828000000_init` through `20260915105019_phase3_owner_mobile_alerts_push`) were scanned for `DROP TABLE`, `DROP COLUMN`, `DROP CONSTRAINT`, and `TRUNCATE`. **None were found.** Every migration is purely additive (`CREATE TABLE`, `ALTER TABLE ... ADD COLUMN`, `CREATE INDEX`, `ADD CONSTRAINT`). No destructive-operation risk identified in the migration history to date.

### D. Schema/migration/code drift — paused "Owner Mobile" feature (documentation-accuracy finding)

The most recent migration, `20260915105019_phase3_owner_mobile_alerts_push`, creates three tables — `device_tokens`, `user_notification_preferences`, `push_configs` — plus two new enums (`PushPlatform`, `MinimumAlertPriority`) and adds `notifiedAt`/`notifiedSeverity` columns to `ai_insights`. **None of this exists in the current `backend/prisma/schema.prisma`** (no `DeviceToken`, `UserNotificationPreference`, or `PushConfig` model; `AiInsight` has no `notifiedAt`/`notifiedSeverity` field). Backend code actively references these models (`backend/src/modules/push/pushService.js`, `backend/src/modules/mobile/pushRegistration.routes.js`, `backend/src/modules/mobile/notificationPreferences.routes.js`), but `backend/src/app.js` contains an explicit, deliberate comment that the corresponding routes are unmounted and this migration "must stay unapplied in production until that work resumes." This is a **known, intentional pause**, not an oversight — but it means:
1. `schema.prisma` is not a complete picture of everything present in the `migrations/` folder.
2. All three tables carry `tenantId` with `ON DELETE CASCADE` from `tenants` in their migration SQL, so — if/when this feature resumes and the migration is applied — tenant isolation for it is already correctly modeled at the DB level.

These three tables are excluded from the 63-entity count above since they are not part of the audited `schema.prisma`, but are documented here per the requirement to review the full migration history.
