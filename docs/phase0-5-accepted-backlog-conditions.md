# Phase 0.5 — Accepted Backlog Conditions

Phase 0.5 (Core vs Industry Module Architecture) was approved and formally closed with conditions by the Product Owner. The three substantive architectural conditions documented in Section K of `phase0-5-module-architecture-verification-report.md` are recorded here as accepted backlog items. Per the Product Owner's instruction, these are **not to be reopened** unless a future phase specifically requires them.

| # | Item | Why it was deferred | Reopen trigger |
|---|---|---|---|
| 1 | `OPTICAL` is registered as one combined industry module (Optical retail + Eye-Clinic clinical workflow) rather than two independently-toggleable modules | `OpticalOrder.patientId`/`clinicalPrescriptionId` link directly into the clinical tables in the current schema; splitting them requires a real schema-level decoupling, which no current tenant need justifies | A future tenant/business case that genuinely needs Optical retail without the clinical workflow (or vice versa) |
| 2 | `ai/analytics.js`, `ai/anomaly.js` (AI module) and `communication/automation.js`'s default templates/rules (Communication module) are not gated by `requireModule('OPTICAL')` | They are Universal Modules, not Core, so the "Core has no Optical/Medical dependency" acceptance criterion does not strictly apply to them; for a tenant with no Optical data they already return empty/zero results, so there is no functional data leak - only an unenforced boundary | A future phase that extends AI/Communication with tenant-facing configuration surfaces where an un-gated Optical-specific function could produce misleading output for a non-Optical tenant |
| 3 | `accounting/ledger.js`'s Chart-of-Accounts seed catalog contains a labeled `OPTICAL_REVENUE` entry even for tenants without the Optical module enabled | The entry is inert - it is only ever inserted into a tenant's actual Chart of Accounts if Optical Orders' own posting logic runs, which cannot happen without the module enabled; removing the catalog entry itself would require the ledger to build its account catalog dynamically per enabled module, a larger refactor with no present behavioral benefit | A future phase that generalizes `accounting/ledger.js` to compose its system-account catalog from each enabled module's own declaration (would naturally resolve this at the same time) |

Two further notes from the same report section were **not** carried forward as backlog items, since they are not architectural gaps requiring future work: the observed transient test-suite DB-connection flakiness is an environment characteristic of the local development Postgres under sustained load (documented, not a defect), and the `MEDICINE` module's minimal scope (schema scaffolding + one report only) is accurately reflected as such in the module registry rather than being an unmet requirement.
