C.1 What changed between the original audit and this update

Between September 16 and September 17, an unrelated backend architecture program found that the Owner Mobile backend routes had been unmounted and its database migration had never been declared in the ORM schema file — a state in which the app's backend could not have served a single request, even in a local test environment. On September 18, this was investigated and restored:

  • Schema/database drift closed: the migration's tables (device tokens, notification preferences, push configuration) had, it turned out, already been silently created in every local test database this whole time — but the ORM's schema file never declared them, so the backend code could not actually use them. The schema file has been corrected to match what the migration already creates. This is a declarative fix only; it changes nothing about what data exists, and was applied to local test databases only, never to production.
  • Routes re-connected locally: the six Owner Mobile API routes were re-connected in the local codebase (not deployed anywhere) so they could be tested again, together with a dedicated login rate-limiter matching the same protection the staff and customer-portal logins already have.
  • A genuine integration gap found and fixed: when the app was originally paused, the scheduled job that is supposed to dispatch push notifications and daily summaries had been disconnected from the rest of the automation pipeline and never reconnected. This was found via the restored test suite (5 tests failed until this was fixed) and has been repaired — this is a real bug fix, not a re-verification.

None of this activates the app for any real business or device. It restores the app to the same "coded, tested, not yet deployed" state the original audit described — now with materially stronger evidence behind that claim than existed on September 16.

Assessment of the deterministic (non-LLM) AI approach

The system uses rules/statistics-based analysis rather than a generative AI chatbot. This is assessed as an acceptable approach for this version — the specification's completion criteria (daily brief, anomaly flags, trend direction, evidence-backed recommendations) are all satisfied without requiring a conversational AI, and the app is explicitly decision-support (data + suggested action), never an automated decision-maker. The two previously-disclosed depth limitations (brief detail level; expense-trend evidence on quiet periods) are both classified as acceptable, deliberate design choices, not defects requiring a fix.

Addendum — Manual On-Device Testing Attempt

Following the original audit, a genuine attempt was made to perform manual, on-device testing of the Android app (login, navigation, and all Phase 1–4 screens) rather than relying on build success alone, as good practice requires.

What was done (September 16): An Android emulator and system image were installed, a local test backend and database were set up with real sample data, and a virtual test device was created.

What blocked completion (September 16): The emulator could not start because hardware virtualization (AMD-V / SVM) appeared disabled at the BIOS/firmware level on the machine used for that attempt — a setting that can only be changed by physically entering the machine's BIOS setup, outside the scope of a software audit.

A second attempt was made September 18 (on the environment used for that day's re-verification, which by then had a working Android SDK, unlike September 16). The existing virtual test device started but failed at a later stage, reporting: "x86_64 emulation currently requires hardware acceleration — Android Emulator hypervisor driver is not installed on this machine." This is a related but distinct failure point from the September 16 attempt (a missing hypervisor driver rather than a BIOS setting), consistent with virtualization support being unavailable in some form on both machines tried so far.

Current status: on-device/manual testing remains NOT VERIFIED, across two separate attempts on two different points of failure. This is disclosed honestly rather than assumed or substituted with build/test-suite success. Once hardware virtualization is enabled and the emulator's hypervisor driver is installed (or a physical Android device is made available), the full manual smoke test (login/logout, Home, Analytics, Alerts, AI Advisor screens, navigation, loading/empty/error states) can be completed and this report updated accordingly.
